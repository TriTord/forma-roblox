Dans la [leçon précédente](/modules/02/l-art-du-prompt-precis/), tu as appris à écrire **un** prompt précis. Mais un jeu, même petit, c’est des dizaines de décisions et plusieurs scripts qui dépendent les uns des autres. La tentation est grande d’écrire « fais-moi un simulator entier » et d’attendre le miracle. Cette leçon te donne la méthode des pros pour l’éviter : **découper**. Et tu vas la voir appliquée de bout en bout, sur un vrai mini-jeu construit prompt par prompt avec Claude Code.

## Pourquoi « fais-moi un simulator entier » ne marche pas

Un prompt géant donne un résultat géant, et c’est justement le problème.

- **Le contexte est limité.** Claude ne « se souvient » que de ce qui tient dans sa fenêtre de contexte (tout ce qu’il a lu et écrit dans la conversation). La documentation officielle de Claude Code le dit sans détour : cette fenêtre se remplit vite, et les performances baissent à mesure qu’elle se remplit. Sur un projet entier, Claude finit par oublier tes premières consignes.
- **Tu ne peux pas relire.** Personne ne relit sérieusement 1 500 lignes produites en une fois. Or, tu l’as vu, relire est **ton** travail : c’est là qu’on attrape les failles de sécurité et les bugs.
- **Tu ne sais plus quoi annuler.** Si le jeu plante, quelle partie est fautive ? Les rounds, la sauvegarde, l’interface ? Avec un seul énorme changement, tu ne peux que tout garder ou tout jeter.
- **L’IA décide à ta place.** Un prompt vague laisse Claude inventer le game design : règles, chiffres, interface. Tu obtiens *un* jeu, pas *ton* jeu.

<Erreur titre="Le prompt « tout-en-un »">
« Fais-moi un simulator complet avec des pets, une boutique, des rebirths et une sauvegarde. » Tu obtiendras peut-être quelque chose qui démarre, mais tu seras incapable de dire si c’est sûr, de le corriger sans tout casser, ou d’ajouter une fonctionnalité sans que Claude réécrive la moitié du reste. Un gros projet se construit **brique par brique**.
</Erreur>

## La méthode : de l’idée au commit

La méthode tient en six étapes. Les deux premières se font une seule fois ; les quatre dernières forment une boucle que tu répètes pour chaque tâche.

```text
1. Mini game design doc (GDD)   → ce que fait le jeu, en une page
2. Plan (mode plan)             → Claude propose, tu corriges, tu valides
3. Liste de petites tâches      → enregistrée dans TACHES.md
   ┌──────────────────────────────────────────────────────────┐
   │ 4. UNE tâche = UN prompt précis                           │
   │ 5. Relecture + test dans Studio (+ selene et StyLua)      │
   │ 6. Commit Git                                             │
   └───────────── tâche suivante (et /clear) ─────────────────┘
```

**1. Le mini game design doc.** Un GDD (*game design document*, document de conception) décrit le jeu du point de vue du joueur : la boucle de jeu, les règles, les chiffres, l’interface, et surtout **ce qui n’est pas dans la version 1**. Une page suffit. Rédige-le toi-même : c’est là que tu prends les décisions de créateur. Enregistre-le dans le projet (`GDD.md`) pour que Claude puisse le lire.

**2. Le plan.** En **mode plan**, Claude lit et explore le projet sans modifier aucun fichier, puis propose une démarche (la [leçon 3](/modules/02/claude-code-de-a-a-z/) explique comment l’activer avec `Shift+Tab` ou `/plan`). Tu lui demandes un plan découpé en tâches, tu le discutes, puis tu le fais enregistrer dans un fichier `TACHES.md`.

**3. Les petites tâches.** Une bonne tâche :

- ajoute **une seule** fonctionnalité, et touche en général 1 à 3 fichiers ;
- peut être **testée seule** dans Studio, avec un critère de réussite clair (« en Play, je vois `Pieces 0` dans le classement ») ;
- se décrit en une phrase. La documentation de Claude Code donne d’ailleurs ce repère : si tu peux décrire le changement en une phrase, il n’y a même pas besoin de plan.

**4. Une tâche par prompt.** Chaque prompt suit le gabarit de la [leçon 4](/modules/02/l-art-du-prompt-precis/) (contexte, existant, objectif, fichiers, contraintes, sécurité, cas limites, vérification). Pas besoin d’y répéter les conventions : ton `CLAUDE.md` les donne déjà à chaque session.

**5. Relire et tester.** Lis ce que Claude a modifié : les changements s’affichent dans la conversation ; `git status` liste les fichiers créés ou modifiés, et `git diff` montre le détail des fichiers déjà enregistrés dans Git (un fichier tout neuf n’y apparaît pas : ouvre-le dans ton éditeur). Lance ensuite `selene` et `StyLua`, puis teste **dans Studio** le critère de réussite de la tâche. La leçon 6 détaille la checklist de relecture.

**6. Commiter.** Quand la tâche marche, enregistre-la dans Git. Dans un deuxième terminal ouvert dans le dossier du projet, tape ces deux commandes l’une après l’autre :

```bash
git add -A
git commit -m "Tâche 1 : configuration du mini-jeu"
```

Tu peux aussi les taper dans Claude Code en commençant la ligne par `!` (mode shell), ou demander à Claude « fais le commit avec le message … ». Chaque commit devient un **point de retour sûr** : si la tâche suivante casse tout, tu reviens à cet état (les checkpoints de Claude Code et `/rewind`, vus en leçon 3, dépannent dans une session, mais la documentation rappelle qu’ils ne remplacent pas Git).

<Astuce titre="Une tâche, une conversation">
Entre deux tâches, tape `/clear` pour repartir d’un contexte vide. Rien n’est perdu : le plan est dans `TACHES.md`, les règles dans `CLAUDE.md`, le code dans les fichiers. Ton prompt commence simplement par « Tâche 4 de TACHES.md ». Claude travaille alors avec un contexte propre, centré sur la tâche du moment.
</Astuce>

## Exemple complet : le mini-jeu « Lave Montante »

Place à la pratique. Tu vas suivre la construction complète d’un mini-jeu à rounds, très courant sur Roblox :

1. les joueurs attendent dans un **lobby** (salle d’attente) ;
2. quand il y a assez de joueurs, une **intermission** (compte à rebours) démarre ;
3. tout le monde est téléporté dans une **arène** ;
4. la **lave monte** : il faut grimper sur les plateformes pour survivre ;
5. les **survivants gagnent des pièces**, puis tout le monde revient au lobby ;
6. le jeu **nettoie** l’arène et recommence.

C’est un projet séparé de l’Obby des Nuages : tu peux le réaliser comme entraînement, dans un nouveau dossier, avant d’appliquer la même méthode à ton obby. Le code final complet est donné à la fin de la leçon.

### Étape 0 : préparer le projet

Crée un projet Rojo versionné avec Git ([leçon 2](/modules/02/installer-un-workflow-pro/)), avec les outils `selene` et `StyLua`, et un `CLAUDE.md` (leçon 3). Pour ce mini-jeu, le `CLAUDE.md` reprend le modèle de la leçon 3 en l’adaptant : il précise en plus que tous les réglages chiffrés vont dans le module `Config`, et que le module `ReglesRound` ne contient que des calculs (sans service Roblox), pour pouvoir le tester automatiquement (leçon 6).

Dans `default.project.json`, déclare dans `ReplicatedStorage` un Folder `Remotes` contenant un RemoteEvent `Notification`, et un Folder vide `EtatRound` (le serveur y publiera l’état du round sous forme d’**attributs**, des valeurs attachées à une instance et répliquées aux clients). Remplace tout le contenu du fichier par celui-ci :

```json
{
  "name": "LaveMontante",
  "tree": {
    "$className": "DataModel",
    "ReplicatedStorage": {
      "$className": "ReplicatedStorage",
      "Modules": {
        "$path": "src/ReplicatedStorage/Modules"
      },
      "Remotes": {
        "$className": "Folder",
        "Notification": { "$className": "RemoteEvent" }
      },
      "EtatRound": {
        "$className": "Folder"
      }
    },
    "ServerScriptService": {
      "$className": "ServerScriptService",
      "$path": "src/ServerScriptService"
    },
    "StarterGui": {
      "$className": "StarterGui",
      "$path": "src/StarterGui"
    },
    "StarterPlayer": {
      "$className": "StarterPlayer",
      "StarterPlayerScripts": {
        "$className": "StarterPlayerScripts",
        "$path": "src/StarterPlayer/StarterPlayerScripts"
      }
    }
  }
}
```

Crée aussi les dossiers vides qu’il cite (`src/ReplicatedStorage/Modules`, `src/ServerScriptService`, `src/StarterGui`, `src/StarterPlayer/StarterPlayerScripts`), sinon Rojo refuse de démarrer. Le `Workspace` n’y figure pas : Rojo ne touche pas au décor que tu construis dans Studio.

Puis construis le décor **à la main** dans Studio (le module 1 t’a appris à le faire) :

- supprime la SpawnLocation du modèle Baseplate ;
- crée un Folder `Lobby` avec un sol et une **SpawnLocation** nommée `ApparitionLobby` (la seule du jeu, pour que les éliminés réapparaissent au lobby) ;
- sélectionne `Workspace` et, dans la fenêtre Properties, décoche `StreamingEnabled` : le mini-jeu est petit, et chaque joueur aura ainsi l’arène déjà chargée quand le serveur l’y téléportera (sinon, son jeu peut se mettre en pause le temps de la charger) ;
- crée un Folder `Arene`, loin du lobby, avec des plateformes ancrées jusqu’à 45 studs de haut, un Folder `PointsApparition` (quelques Parts ancrées, invisibles, sans collision, posées au sol de l’arène) et une Part `DepartLave` (ancrée, à plat, invisible, sans collision, aussi large que l’arène et posée à son niveau de sol).

### Le mini game design doc

Voici le `GDD.md` du jeu. Il tient en une page, et chaque chiffre y est décidé par toi, pas par l’IA.

```markdown
# Lave Montante — mini game design doc (v1)

## Le jeu en une phrase
Des rounds courts : les joueurs attendent dans un lobby, sont téléportés dans une arène,
et doivent grimper pour échapper à la lave qui monte. Les survivants gagnent des pièces.

## Boucle de jeu
1. Attente dans le lobby tant qu'il y a moins de JOUEURS_MIN joueurs.
2. Intermission : compte à rebours de 15 s dans le lobby.
3. Round de 60 s au maximum : téléportation dans l'arène ; 5 s de répit, puis la lave
   monte régulièrement pour atteindre 40 studs à la fin des 60 s.
4. Un joueur touché par la lave est éliminé (il réapparaît dans le lobby).
5. Fin : chaque survivant gagne 25 pièces (+25 s'il est le dernier survivant d'un round
   à plusieurs) et 1 victoire, puis retour au lobby.
6. On recommence.

## Règles
- Le serveur décide de tout : phases, chronomètre, élimination, récompenses. Le client n'envoie rien.
- Un joueur qui arrive pendant un round attend le suivant dans le lobby.
- Un joueur qui part pendant un round est retiré proprement.
- Entre deux rounds, il ne reste rien : lave détruite, connexions coupées, participants oubliés.

## Interface
- Un bandeau en haut : « En attente de joueurs (1/2) », « Prochain round dans 12 s »,
  « La lave monte ! Encore 34 s », « Fin du round : 2 survivant(s) ».
- Un message personnel au survivant : « Tu as survécu ! +25 pièces ».

## Hors périmètre de la v1
Sauvegarde des pièces (DataStore), boutique, plusieurs arènes, sons, classement global.
```

Remarque la dernière section : dire ce qu’on **ne fait pas** protège la v1 contre l’ajout sans fin de fonctionnalités (le *scope creep* du module 0).

### Tâche 3 : les règles du round, testées

Cette tâche isole les **calculs** du jeu dans un module sans aucun service Roblox. Avantage : on peut les vérifier automatiquement, en une seconde, sans lancer Studio, avec **Lune** (un programme qui exécute du Luau en dehors de Roblox). Installe-le dans le dossier du projet avec `rokit add lune-org/lune` ; la leçon 6 explique en détail ces tests.

<Prompt titre="Tâche 3 : ReglesRound">

```text
Contexte : tâche 3 de TACHES.md. Config existe (tâche 1).
Objectif : un ModuleScript de calculs purs, utilisé par le serveur, et ses tests automatiques.
Fichiers concernés : crée src/ReplicatedStorage/Modules/ReglesRound.luau et tests/ReglesRound.spec.luau. Ne modifie rien d'autre.
Contraintes techniques : ReglesRound ne contient AUCUN service Roblox ni instance (il doit tourner avec Lune). Fonctions, avec des paramètres explicites (pas de require de Config) :
```

```luau
-- ModuleScript « ReglesRound » dans ReplicatedStorage > Modules
-- Les règles du round sous forme de calculs PURS : aucun service Roblox, aucune instance.
-- C'est ce qui permet de les tester automatiquement en dehors de Studio (module 2, leçon 6).
local ReglesRound = {}

-- Vrai si assez de joueurs sont connectés pour lancer un round
function ReglesRound.assezDeJoueurs(nombreJoueurs: number, minimum: number): boolean
	return nombreJoueurs >= minimum
end

-- Hauteur de la lave (en studs au-dessus de son point de départ) après « tempsEcoule » secondes de round.
-- La lave attend « delai » secondes, puis monte régulièrement jusqu'à « hauteurMax » à la fin du round.
function ReglesRound.hauteurLave(tempsEcoule: number, delai: number, dureeRound: number, hauteurMax: number): number
	if tempsEcoule <= delai then
		return 0
	end
	local progression = (tempsEcoule - delai) / (dureeRound - delai)
	return math.clamp(progression, 0, 1) * hauteurMax
end

-- Vrai si le centre du personnage (sa HumanoidRootPart) est passé sous le dessus de la lave
function ReglesRound.estSousLaLave(hauteurJoueur: number, hauteurDessusLave: number): boolean
	return hauteurJoueur < hauteurDessusLave
end

-- Pièces gagnées par CHAQUE survivant à la fin du round
function ReglesRound.recompense(
	nombreSurvivants: number,
	nombreParticipants: number,
	base: number,
	bonusDernier: number
): number
	if nombreSurvivants <= 0 then
		return 0
	end
	if nombreSurvivants == 1 and nombreParticipants >= 2 then
		return base + bonusDernier -- le dernier survivant d'un round à plusieurs gagne un bonus
	end
	return base
end

return ReglesRound
```

```luau
-- ModuleScript « Lave » dans ServerScriptService (côté serveur)
-- Crée la lave d'un round, la fait monter et donne la hauteur de son dessus.
local Lave = {}

local EPAISSEUR_MIN = 0.2 -- une Part ne peut pas avoir une taille nulle

-- Crée une Part de lave posée sur « depart » (la Part repère DepartLave de l'arène)
function Lave.creer(depart: BasePart, parent: Instance): BasePart
	local lave = Instance.new("Part")
	lave.Name = "Lave"
	lave.Anchored = true
	lave.CanCollide = false -- on la traverse : c'est le serveur qui élimine, pas une collision
	lave.CanTouch = false -- on n'utilise pas Touched (voir la leçon : peu fiable ici)
	lave.CanQuery = false
	lave.CastShadow = false
	lave.Material = Enum.Material.Neon
	lave.Color = Color3.fromRGB(255, 85, 0)
	lave.Transparency = 0.2
	lave.Size = Vector3.new(depart.Size.X, EPAISSEUR_MIN, depart.Size.Z)
	lave.CFrame = CFrame.new(depart.Position + Vector3.new(0, EPAISSEUR_MIN / 2, 0))
	lave.Parent = parent
	return lave
end

-- Place le dessus de la lave à « hauteur » studs au-dessus du centre de « depart »
function Lave.mettreAHauteur(lave: BasePart, depart: BasePart, hauteur: number)
	local epaisseur = math.max(hauteur, EPAISSEUR_MIN)
	lave.Size = Vector3.new(lave.Size.X, epaisseur, lave.Size.Z)
	lave.CFrame = CFrame.new(depart.Position + Vector3.new(0, epaisseur / 2, 0))
end

-- Hauteur (coordonnée Y) du dessus de la lave
function Lave.dessus(lave: BasePart): number
	return lave.Position.Y + lave.Size.Y / 2
end

return Lave
```

```luau
local Players = game:GetService("Players")
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local ServerScriptService = game:GetService("ServerScriptService")
local Workspace = game:GetService("Workspace")

local modules = ReplicatedStorage:WaitForChild("Modules")
local Config = require(modules:WaitForChild("Config"))
local ReglesRound = require(modules:WaitForChild("ReglesRound"))
local Lave = require(ServerScriptService:WaitForChild("Lave"))

local etatRound = ReplicatedStorage:WaitForChild("EtatRound")
local notification = ReplicatedStorage:WaitForChild("Remotes"):WaitForChild("Notification") :: RemoteEvent

-- Construits à la main dans Studio (voir le README)
local apparitionLobby = Workspace:WaitForChild("Lobby"):WaitForChild("ApparitionLobby") :: BasePart
local arene = Workspace:WaitForChild("Arene")
local dossierPoints = arene:WaitForChild("PointsApparition")
local departLave = arene:WaitForChild("DepartLave") :: BasePart

type Participant = {
	personnage: Model,
	connexionMort: RBXScriptConnection,
}

-- Joueurs encore en vie dans le round en cours
local participants: { [Player]: Participant } = {}
local laveActuelle: BasePart? = nil

-- L'état du round est publié dans des attributs : le client les lit, il n'envoie jamais rien
local function changerPhase(phase: string, tempsRestant: number)
	etatRound:SetAttribute("Phase", phase)
	etatRound:SetAttribute("TempsRestant", tempsRestant)
end

local function compterParticipants(): number
	local nombre = 0
	for _ in participants do
		nombre += 1
	end
	return nombre
end

-- Retire un joueur du round (éliminé, parti ou fin du round) et coupe sa connexion
local function retirerParticipant(player: Player)
	local participant = participants[player]
	if participant then
		participant.connexionMort:Disconnect()
		participants[player] = nil
	end
end

local function teleporter(personnage: Model, cible: BasePart)
	-- PivotTo déplace tout le personnage d'un coup ; +4 studs pour ne pas apparaître dans le sol
	personnage:PivotTo(cible.CFrame + Vector3.new(0, 4, 0))
end

local function listerPointsApparition(): { BasePart }
	local points: { BasePart } = {}
	for _, enfant in dossierPoints:GetChildren() do
		if enfant:IsA("BasePart") then
			table.insert(points, enfant)
		end
	end
	return points
end

-- Remet tout à zéro : appelée à la fin de CHAQUE round, même après une erreur.
-- Les participants encore en vie reviennent au lobby : personne ne reste coincé dans l'arène.
local function nettoyerRound()
	if laveActuelle then
		laveActuelle:Destroy()
		laveActuelle = nil
	end
	for player, participant in participants do
		retirerParticipant(player)
		local personnage = participant.personnage
		local humanoid = personnage:FindFirstChildOfClass("Humanoid")
		-- Ceux qui sont morts ou partis ont déjà été retirés (connexion Died, PlayerRemoving)
		if personnage.Parent ~= nil and humanoid and humanoid.Health > 0 then
			teleporter(personnage, apparitionLobby)
		end
	end
end

local function attendreJoueurs()
	while not ReglesRound.assezDeJoueurs(#Players:GetPlayers(), Config.JOUEURS_MIN) do
		changerPhase("Attente", 0)
		task.wait(1)
	end
end

-- Compte à rebours dans le lobby ; renvoie false si des joueurs partent entre-temps
local function intermission(): boolean
	for reste = Config.DUREE_INTERMISSION, 1, -1 do
		if not ReglesRound.assezDeJoueurs(#Players:GetPlayers(), Config.JOUEURS_MIN) then
			return false
		end
		changerPhase("Intermission", reste)
		task.wait(1)
	end
	return true
end

-- Téléporte dans l'arène chaque joueur vivant et l'inscrit au round ; renvoie leur nombre
local function demarrerRound(): number
	local points = listerPointsApparition()
	if #points == 0 then
		error("Aucune Part dans Workspace.Arene.PointsApparition")
	end
	for index, player in Players:GetPlayers() do
		local personnage = player.Character
		local humanoid = if personnage then personnage:FindFirstChildOfClass("Humanoid") else nil
		if personnage and humanoid and humanoid.Health > 0 then
			teleporter(personnage, points[(index - 1) % #points + 1])
			participants[player] = {
				personnage = personnage,
				connexionMort = humanoid.Died:Connect(function()
					retirerParticipant(player) -- mort (lave, chute, reset) : éliminé
				end),
			}
		end
	end
	return compterParticipants()
end

-- Fait monter la lave et élimine ceux qu'elle rattrape, jusqu'à la fin du temps ou du dernier survivant
local function jouerRound()
	local lave = Lave.creer(departLave, arene)
	laveActuelle = lave
	local debut = os.clock()
	while true do
		local ecoule = os.clock() - debut
		local hauteur =
			ReglesRound.hauteurLave(ecoule, Config.DELAI_AVANT_LAVE, Config.DUREE_ROUND, Config.HAUTEUR_MAX_LAVE)
		Lave.mettreAHauteur(lave, departLave, hauteur)
		local dessusLave = Lave.dessus(lave)

		-- C'est le SERVEUR qui regarde où sont les personnages : le client ne déclare rien
		for player, participant in participants do
			local personnage = participant.personnage
			local racine = personnage.PrimaryPart
			local humanoid = personnage:FindFirstChildOfClass("Humanoid")
			if racine == nil or humanoid == nil or personnage.Parent == nil then
				retirerParticipant(player) -- personnage disparu : on ne le compte plus
			elseif ReglesRound.estSousLaLave(racine.Position.Y, dessusLave) then
				humanoid.Health = 0
				retirerParticipant(player)
			end
		end

		changerPhase("EnJeu", math.max(0, math.ceil(Config.DUREE_ROUND - ecoule)))
		if ecoule >= Config.DUREE_ROUND or compterParticipants() == 0 then
			return
		end
		task.wait(Config.INTERVALLE_VERIFICATION)
	end
end

local function recompenser(player: Player, gain: number)
	local leaderstats = player:FindFirstChild("leaderstats")
	if leaderstats == nil then
		return
	end
	local pieces = leaderstats:FindFirstChild("Pieces")
	local victoires = leaderstats:FindFirstChild("Victoires")
	if pieces and pieces:IsA("IntValue") then
		pieces.Value += gain
	end
	if victoires and victoires:IsA("IntValue") then
		victoires.Value += 1
	end
end

-- Récompense les survivants et affiche le résultat (nettoyerRound les ramène ensuite au lobby)
local function terminerRound(nombreDepart: number)
	local survivants: { Player } = {}
	for player in participants do
		table.insert(survivants, player)
	end
	local gain =
		ReglesRound.recompense(#survivants, nombreDepart, Config.RECOMPENSE_SURVIE, Config.BONUS_DERNIER_SURVIVANT)
	for _, player in survivants do
		recompenser(player, gain)
		notification:FireClient(player, `Tu as survécu ! +{gain} pièces`)
	end

	etatRound:SetAttribute("Survivants", #survivants)
	changerPhase("Fin", Config.DUREE_FIN_ROUND)
	task.wait(Config.DUREE_FIN_ROUND)
end

local function jouerUnCycle()
	local nombreDepart = demarrerRound()
	if nombreDepart == 0 then
		return -- personne n'avait de personnage vivant : on recommence l'intermission
	end
	jouerRound()
	terminerRound(nombreDepart)
end

-- Un joueur qui quitte le jeu en plein round ne doit plus être compté
Players.PlayerRemoving:Connect(retirerParticipant)

changerPhase("Attente", 0)
while true do
	attendreJoueurs()
	if intermission() then
		-- pcall : une erreur pendant un round ne doit pas arrêter le jeu pour toujours
		local ok, erreur = pcall(jouerUnCycle)
		if not ok then
			warn("Round interrompu :", erreur)
		end
		nettoyerRound() -- toujours appelé, même après une erreur : retour au lobby, connexions coupées, lave détruite
	end
end
```

<Astuce titre="Le plan est un document vivant">
Si, en cours de route, tu découvres une tâche oubliée (un bug, un cas limite), ne l’ajoute pas en douce à la tâche en cours : note-la dans `TACHES.md` et traite-la à son tour, avec son propre prompt et son propre commit. Ton historique Git reste lisible, et chaque commit fait une seule chose.
</Astuce>

<Resume>
- Ne demande jamais un jeu entier en un prompt : le contexte se remplit, tu ne peux plus relire, et tu ne sais plus quoi annuler.
- La méthode : mini GDD écrit par toi → plan en mode plan → liste de petites tâches dans `TACHES.md`.
- Puis, pour chaque tâche : **un prompt précis → relecture et test dans Studio → commit Git**, avec `/clear` entre deux tâches.
- Une bonne tâche ajoute une seule fonctionnalité, touche peu de fichiers et a un critère de réussite testable.
- Quand le résultat n’est pas bon, écris un prompt ciblé : symptôme observé, cause, solution attendue, vérification.
- Isoler les calculs dans un module pur (comme `ReglesRound`) permet de les tester automatiquement.
</Resume>
