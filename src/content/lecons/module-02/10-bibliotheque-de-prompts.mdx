Tu connais maintenant la méthode : un prompt précis, une tâche à la fois, une vérification à la fin. Cette page est ta **boîte à outils** : un prompt prêt à copier pour chaque système courant d’un jeu Roblox, de la sauvegarde au combat en passant par la boutique. Chaque prompt suit le gabarit en huit rubriques de la [leçon 4](/modules/02/l-art-du-prompt-precis/) et reprend exactement les règles enseignées dans les leçons techniques de la formation. Garde-la sous la main : tu y reviendras à chaque nouveau système.

**Cette page ne se lit pas d’une traite.** Lis d’abord la section « Comment utiliser cette bibliothèque » juste en dessous (cinq minutes), puis va directement au prompt dont tu as besoin grâce au tableau « Quel prompt pour quel besoin ? » ou à la table des matières. Beaucoup de ces systèmes sont construits plus loin dans la formation (modules 3 à 10) : n’utilise un prompt qu’après avoir lu la leçon indiquée dans « Détails », sinon tu ne pourras pas vérifier le code produit.

## Comment utiliser cette bibliothèque

Chaque prompt est présenté de la même façon :

1. **Avant le prompt** : quand l’utiliser, ce qu’il faut adapter, et la leçon qui explique le système en détail.
2. **Le prompt**, dans un cadre avec un bouton **Copier**.
3. **Après le prompt** : les points à vérifier dans le code produit par Claude Code.

### Adapter les crochets

Tout ce qui est écrit `[EN_MAJUSCULES_ENTRE_CROCHETS]` est à remplacer par **ta** valeur : le nom de ton jeu, un prix, une durée, l’ID d’un produit. Quand un exemple est donné (`[DUREE_PARTIE, ex. 120]`), remplace tout le crochet, exemple compris. Le plus simple : colle d’abord le prompt dans un éditeur de texte (Bloc-notes sous Windows, TextEdit sous Mac, ou VS Code), remplis les crochets, puis copie le résultat dans Claude Code. Si une rubrique ne concerne pas ton jeu, supprime la ligne, mais garde toujours « Objectif » et « Vérification ».

Trois formes particulières :

- un crochet qui propose un **choix** (`[RIEN / le ModuleScript …]`, `[OU : contre des PNJ]`) : garde seulement la version qui correspond à ton jeu, sans les crochets ni le « OU » ;
- un crochet qui commence par **COLLE** (`[COLLE ICI L'ERREUR]`, `[COLLE TES CHIFFRES …]`) : colle à sa place le texte exact, sans le résumer ;
- les petits noms comme `[NOM]` : un mot court sans espace ni accent (par exemple `TrailDore`), parce qu’il entre dans un nom de fichier ou d’attribut.

Les prompts utilisent les noms du fil rouge (`DonneesJoueurs`, `Validation`, `ReplicatedStorage.Remotes`, DataStore `DonneesJoueurs_v1`…). Si ton jeu utilise d’autres noms, remplace-les partout, sans en oublier un.

<Erreur titre="Envoyer un prompt avec des crochets non remplis">
Un prompt qui contient encore `[ID_DU_PRODUIT]` ou `[MONNAIE]` oblige Claude Code à deviner, et il devinera mal : un ID à 0 oublié, une monnaie qui n’existe pas, un fichier au mauvais endroit. Avant d’envoyer, cherche le caractère `[` dans ton texte : il ne doit plus rester aucun mot en majuscules entre crochets (seuls restent le préfixe `[DEBUG]` et le code, comme `inventaire[idObjet]`).
</Erreur>

### Un prompt, une tâche

Chaque prompt construit **un** système. Entre deux systèmes, tape `/clear` pour repartir d’un contexte propre (leçon 3) : la conversation précédente ne pollue plus la suivante. Ne colle jamais plusieurs prompts à la suite dans le même message.

### Le mode plan pour les gros systèmes

Les prompts qui touchent plusieurs fichiers ou des données sensibles (sauvegarde, achats en Robux, combat, manches, audits) commencent par « Commence par me proposer un plan (mode plan), sans modifier de fichier. » Active en plus le mode plan avant de coller le prompt : appuie sur `Shift+Tab` jusqu’à voir `⏸ plan mode on` dans la barre d’état (sous Windows, si `Shift+Tab` ne change rien, essaie `Alt+M`). Lis le plan, corrige-le si besoin, puis accepte-le.

### Tester, puis commiter

Après chaque système : fais les tests de la rubrique « Vérification » dans Studio, relis les points « À vérifier », puis enregistre une version qui marche avec Git (leçon 2) :

```bash
git add -A
git commit -m "Ajout de la boutique sécurisée"
```

Si le système suivant casse tout, tu pourras toujours revenir à ce commit.

### Le CLAUDE.md fait le reste

Ces prompts supposent que ton projet a déjà son fichier **CLAUDE.md** ([leçon 3](/modules/02/claude-code-de-a-a-z/)). Il rappelle à chaque session l’architecture, les conventions de nommage, « toujours `task.wait`, jamais `wait` », les `pcall` autour des DataStores et de MarketplaceService, et la règle d’or : le serveur valide tout. C’est pour ça que les prompts ne répètent pas toutes ces règles et se concentrent sur ce qui est propre à chaque système.

<Attention>

Ne colle **jamais** dans un prompt un mot de passe, ton cookie `.ROBLOSECURITY`, une clé d’API ou un autre secret, même pour « aider » Claude Code. Les IDs de Game Pass et de Developer Product ne sont pas des secrets : tu peux les écrire. Et pour tout ce qui touche aux Robux (créer un produit, faire un vrai achat de test), si tu es mineur, fais-le avec un adulte.

Rappel : Claude Code est réservé aux 18 ans et plus (conditions d’utilisation d’Anthropic, octobre 2026). Si tu as moins de 18 ans, utilise ces prompts avec un adulte qui a son propre compte, ou sers-t’en comme d’un plan pour écrire le code toi-même (ou avec l’Assistant de Studio) : les points « À vérifier » restent les mêmes.

</Attention>

## Démarrage de projet

### Le fichier CLAUDE.md du projet

**Quand l’utiliser :** une fois, juste après avoir installé Rojo et Git ([leçon 2](/modules/02/installer-un-workflow-pro/)), ou pour améliorer un CLAUDE.md créé par `/init`. Le modèle complet est dans la [leçon 3](/modules/02/claude-code-de-a-a-z/) : ce prompt le fait adapter à **ton** projet réel. **À adapter :** `[NOM_DU_JEU]`, `[DESCRIPTION_EN_UNE_PHRASE]`.

<Prompt titre="Générer ou adapter le CLAUDE.md">

```text
Contexte : je crée le jeu Roblox [NOM_DU_JEU] ([DESCRIPTION_EN_UNE_PHRASE]). C'est un projet Rojo versionné avec Git. Je débute et je relis chaque modification.
Ce qui existe déjà : default.project.json et le dossier src/ (Scripts .server.luau, LocalScripts .client.luau, ModuleScripts .luau). Peut-être un CLAUDE.md créé par /init.
Objectif : un fichier CLAUDE.md à la racine qui te permet, à chaque session, de coder avec les règles de ce projet sans que je les répète.
Fichiers concernés : CLAUDE.md uniquement (crée-le, ou complète celui qui existe sans supprimer ce qui est juste). Ne modifie rien d'autre.
Contraintes techniques :
- Lis d'abord default.project.json et tous les fichiers de src/. N'invente aucun dossier, script ou remote qui n'existe pas.
- Moins de 200 lignes, en français, en listes courtes.
- Sections : 1) Le jeu (2 phrases) ; 2) Architecture : chaque dossier de src/ et son emplacement dans Studio d'après default.project.json ; 3) Services utilisés ; 4) Conventions de nommage : identifiants en français sans accents, PascalCase pour les scripts et les instances, camelCase pour les variables, suffixes Rojo ; 5) Remotes : liste de ReplicatedStorage.Remotes, tous déclarés dans default.project.json ; 6) Données : DataStore "DonneesJoueurs_v1", clé "Joueur_" .. player.UserId, module DonneesJoueurs ; 7) Règles de code ; 8) Règles de sécurité ; 9) Commandes de vérification ; 10) Méthode de travail.
- Règles de code : toujours task.wait, task.spawn et task.delay, jamais wait, spawn ni delay ; game:GetService pour chaque service ; pcall autour de chaque appel DataStore et MarketplaceService ; connexions et tables indexées par joueur nettoyées (PlayerRemoving) ; aucune API dépréciée.
- Règles de sécurité : le serveur valide tout, le client ne fait que demander ; jamais de prix, de récompense, de dégâts ni de position décidés par le client ; chaque OnServerEvent vérifie le type, la valeur (math.isfinite pour les nombres), le contexte et le débit.
- Commandes de vérification : selene src et stylua --check src.
- Méthode : proposer un plan avant tout changement qui touche plus de 2 fichiers ; ne modifier que les fichiers demandés ; si tu n'es pas sûr qu'une API Roblox existe, le dire au lieu de l'inventer.
Sécurité : n'écris dans CLAUDE.md aucun mot de passe, cookie, clé d'API ni identifiant de connexion.
Vérification : affiche le fichier final, puis indique pour chaque section le fichier du projet d'où vient l'information. Je le relirai, puis je vérifierai avec /context qu'il est bien chargé.
```

</Prompt>

**À vérifier dans le code produit :**

- chaque dossier et chaque remote cités existent vraiment dans `default.project.json` et `src/` (aucune invention) ;
- les règles de sécurité et « `task.wait`, jamais `wait` » sont présentes ;
- le fichier reste court (moins de 200 lignes) : une ligne inutile, c’est une ligne que Claude Code risque de mal suivre ;
- aucun secret n’y figure.

### Planifier un jeu à partir d’un GDD

**Quand l’utiliser :** au début d’un nouveau jeu, quand tu as écrit ton game design doc (GDD) dans le fichier `GDD.md` à la racine du projet ([leçon 5](/modules/02/decouper-un-gros-projet/)). Active le mode plan avant. Le plan validé est enregistré dans `TACHES.md`, comme à la leçon 5. **À adapter :** `[NOM_DU_JEU]`, `[GENRE]`, `[NOMBRE_MAX_DE_TACHES]`. Le `@` devant un chemin indique à Claude Code de lire ce fichier.

<Prompt titre="Planifier le jeu à partir du GDD">

```text
Commence par me proposer un plan (mode plan), sans modifier de fichier.
Contexte : je veux créer [NOM_DU_JEU], un jeu Roblox de type [GENRE]. Mon game design doc est dans @GDD.md. Je débute : je veux une version 1 jouable et publiable, pas tout le jeu rêvé.
Ce qui existe déjà : le projet Rojo (default.project.json, src/) et le CLAUDE.md du projet.
Objectif : un plan de construction découpé en petites tâches, chacune faisable avec UN prompt, testable dans Studio, puis commitée avant de passer à la suivante.
Fichiers concernés : aucun pendant le plan. Seulement après mon accord, écris la liste des tâches dans TACHES.md, et ne touche à rien d'autre.
Contraintes techniques :
- Sépare la « version 1 » (le minimum pour que la boucle de jeu fonctionne) et « plus tard ».
- Au plus [NOMBRE_MAX_DE_TACHES] tâches pour la version 1, dans l'ordre des dépendances (par exemple la sauvegarde avant la boutique).
- Pour chaque tâche : nom ; ce que le joueur voit ou fait ; fichiers à créer ou modifier (chemins Rojo) ; remotes ou champs de données ajoutés ; dépendances ; critère de réussite testable dans Studio en moins de 5 minutes.
- Marque les tâches à risque (sécurité, sauvegarde, achats en Robux).
Sécurité : pour chaque tâche où le client envoie une demande au serveur, écris ce que le serveur devra valider.
Cas limites : si le GDD est flou ou contradictoire, pose-moi d'abord jusqu'à 5 questions au lieu de deviner.
Vérification : termine par la liste des questions encore ouvertes, puis par la tâche n°1 rédigée en prompt complet avec les rubriques Contexte, Ce qui existe déjà, Objectif, Fichiers concernés, Contraintes techniques, Sécurité, Cas limites et Vérification.
```

</Prompt>

**À vérifier dans le plan produit :**

- la version 1 est vraiment petite (si elle contient 40 tâches, ce n’est plus une version 1) ;
- chaque tâche a un critère de réussite que **tu** peux tester toi-même ;
- l’ordre respecte les dépendances (pas de boutique avant la sauvegarde, pas d’achat en Robux avant la boutique) ;
- les tâches à risque sont signalées et indiquent ce que le serveur valide.

### La boîte à outils de validation

**Quand l’utiliser :** avant tout système qui reçoit des demandes des clients. Plusieurs prompts de cette page utilisent ce module. Il reprend celui de la leçon [Ne jamais faire confiance au client](/modules/04/ne-jamais-faire-confiance-au-client/). **À adapter :** `[NOM_DU_JEU]`.

<Prompt titre="Module Validation">

```text
Contexte : jeu [NOM_DU_JEU]. Plusieurs Scripts serveur vont recevoir des demandes des clients et des contacts (Touched) : je veux les mêmes vérifications partout.
Ce qui existe déjà : le CLAUDE.md du projet.
Objectif : un ModuleScript de validation réutilisable par tous les Scripts serveur.
Fichiers concernés : crée src/ServerScriptService/Validation.luau uniquement.
Contraintes techniques : fonctions estNombre(valeur, min, max) qui rejette NaN et l'infini avec math.isfinite ; estEntier(valeur, min, max) ; estTexte(valeur, longueurMax) : non vide, pas trop long, UTF-8 valide (utf8.len) ; racineVivante(player) : la HumanoidRootPart si le Humanoid est vivant, sinon nil ; estAPortee(player, position, distanceMax) ; creerCooldown(delai) qui renvoie une fonction (player) -> boolean, mesure le temps avec os.clock et oublie le joueur à PlayerRemoving. Les valeurs venant du client sont typées unknown.
Sécurité : le module reste dans ServerScriptService, que les clients ne peuvent pas lire.
Cas limites : nil, table ou texte à la place d'un nombre ; 2.5 pour un entier ; joueur sans personnage.
Vérification : donne-moi les lignes à coller dans la Command Bar (en Play, vue serveur) qui affichent estEntier(x, 1, 10) pour 3, 2.5, 0/0, math.huge, "3" et nil : seul 3 doit donner true. selene src et stylua --check src sans erreur.
```

</Prompt>

**À vérifier dans le code produit :**

- `estNombre` appelle `math.isfinite` **avant** de comparer aux bornes (NaN échappe à toutes les comparaisons) ;
- chaque fonction teste d’abord `typeof(...)` avant d’utiliser la valeur ;
- `creerCooldown` vide sa table à `PlayerRemoving` (sinon elle grossit sans fin) ;
- le fichier est bien dans `src/ServerScriptService/`, pas dans `ReplicatedStorage`.

## Bases de l’obby

### Checkpoints sécurisés

**Quand l’utiliser :** pour la progression d’un obby. Détails : [Sécuriser l’Obby des Nuages](/modules/04/securiser-l-obby/). **À adapter :** `[NOMBRE_DE_CHECKPOINTS]`, `[DISTANCE_MAX]` (15 studs dans le fil rouge, plus si tes checkpoints sont grands), `[TEMPS_MIN_ETAPE]` (2 secondes dans le fil rouge).

<Prompt titre="Checkpoints sécurisés">

## Débogage

### Prompt type pour une erreur

**Quand l’utiliser :** dès qu’une erreur rouge apparaît dans l’Output ou qu’un système ne fait pas ce qu’il devrait. La méthode complète est dans [Déboguer avec l’IA](/modules/02/deboguer-avec-l-ia/). C’est le même modèle que dans cette leçon, avec les six informations à donner (l’erreur complète, le script, l’attendu, l’obtenu, les étapes pour reproduire, ce que tu as déjà essayé). **À adapter :** tout ce qui est entre crochets, et surtout l’erreur **complète**.

<Prompt titre="Déboguer une erreur">

```text
Contexte : jeu [NOM_DU_JEU]. Le système [NOM_DU_SYSTEME] ne marche plus depuis [QUAND, ex. mon dernier commit « ajout de la boutique »].
Erreur complète copiée depuis l'Output (le texte rouge ET toutes les lignes entre Stack Begin et Stack End) :
[COLLE ICI L'ERREUR]
Fichiers concernés : @[CHEMIN_DU_SCRIPT, ex. src/ServerScriptService/Boutique.server.luau] ; lis aussi les fichiers cités dans la pile.
Comportement attendu : [CE QUI DEVRAIT SE PASSER, du point de vue du joueur].
Comportement obtenu : [CE QUI SE PASSE VRAIMENT].
Pour reproduire : [ÉTAPES EXACTES, ex. Play, toucher le checkpoint 2, ouvrir la boutique, cliquer sur Acheter].
Ce que j'ai déjà essayé : [CE QUE TU AS TESTÉ ET LE RÉSULTAT, ou « rien »].
Objectif : trouver la cause réelle et la corriger avec le plus petit changement possible.
Contraintes techniques : ne modifie rien tout de suite. 1) Explique l'erreur en une ou deux phrases simples. 2) Propose au plus 3 hypothèses, de la plus probable à la moins probable. 3) Pour la première, dis-moi quel print ajouter (fichier, ligne, valeur affichée, préfixe [DEBUG]) pour la confirmer. Une hypothèse à la fois. Ne réécris pas tout le script et ne touche à aucun autre système.
Sécurité : la correction ne doit retirer aucune vérification côté serveur ni déplacer une décision vers le client.
Vérification : une fois la cause confirmée, corrige, retire les print [DEBUG], et dis-moi exactement quoi refaire dans Studio pour vérifier que l'erreur a disparu. selene src et stylua --check src sans erreur.
```

</Prompt>

**À vérifier dans la réponse :**

- l’explication de l’erreur correspond à la ligne citée dans la pile d’appels ;
- la correction est petite et ciblée (méfie-toi d’un script entièrement réécrit) ;
- les `print` de diagnostic (préfixe `[DEBUG]`) ont été retirés ;
- si Claude Code tourne en rond après deux corrections ratées, tape `/clear` et repars de ce prompt, complété par ce que tu as appris.

<Resume>
- Chaque prompt de la bibliothèque suit le gabarit en huit rubriques : remplace **tous** les crochets par les vraies valeurs de ton jeu avant de l’envoyer.
- Un prompt, une tâche : mode plan pour les gros systèmes, `/clear` entre deux systèmes, tests de la rubrique « Vérification », puis commit.
- Les règles de sécurité sont dans chaque prompt : le client demande, le serveur décide (prix, dégâts, récompenses, achats).
- Les points « À vérifier » sont ta part du travail : un prompt précis donne un meilleur code, pas un code garanti.
- Garde tes versions adaptées dans ton projet, et transforme les plus utilisées en skills.
</Resume>
