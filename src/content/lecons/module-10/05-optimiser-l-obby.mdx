C’est le moment de tout mettre en pratique. Dans cette leçon, tu vas réaliser un **audit de performance** complet de l’Obby des Nuages : mesurer, passer une checklist, corriger, vérifier, documenter. C’est exactement le cycle « identifier, améliorer, surveiller » que décrit la documentation Roblox. À la fin, tu auras un obby plus fluide sur mobile, et la preuve chiffrée du gain.

## Étape 1 : préparer l’audit

### Fais une sauvegarde

Avant de toucher à quoi que ce soit, garde une copie de ton jeu : **File** › **Save to File As** pour une copie locale, ou appuie-toi sur l’historique des versions publiées (vu au module 1). Si une optimisation tourne mal, tu pourras revenir en arrière.

### Choisis tes conditions de mesure

Pour que « avant » et « après » soient comparables, fixe tes conditions une fois pour toutes :

- **le même appareil** : ton téléphone de référence de la leçon 1 (et ton PC en complément) ;
- **le même parcours** : par exemple, du spawn jusqu’à l’étape 10, en ramassant les pièces sur le chemin ;
- **la même durée** : environ 5 minutes de jeu, plus une session de 10 à 15 minutes pour la surchauffe ;
- **le vrai jeu publié**, pas Studio, pour les chiffres de FPS et de mémoire.

### Remplis ta fiche de mesure « avant »

Recopie ce tableau dans un document ou un tableur :

| Mesure | Outil | Avant | Après |
| :--- | :--- | :--- | :--- |
| FPS moyen sur le parcours | Performance Stats | | |
| FPS dans la zone la plus chargée | Performance Stats | | |

## Étape 2 : passer la checklist

Passe chaque catégorie, coche ce qui est bon, note ce qui ne l’est pas. Ne corrige rien pour l’instant : d’abord l’inventaire.

### Scripts

- [ ] Aucune boucle `while true` ni connexion `Heartbeat` / `PreRender` qui pourrait être remplacée par un événement.
- [ ] Les références (`GetService`, `WaitForChild`) sont récupérées une fois, pas à chaque image.
- [ ] Le Script Profiler (client puis serveur) ne montre aucune fonction à toi anormalement coûteuse.
- [ ] Aucune erreur répétée dans le Log : une erreur qui se produit à chaque image coûte aussi du temps.

### Mémoire

- [ ] Les connexions faites par joueur sont déconnectées à son départ (ou `PlayerCharacterDestroyBehavior` est sur `Enabled`).
- [ ] Les tables indexées par joueur sont vidées dans `PlayerRemoving`.
- [ ] `LuaHeap` et `InstanceCount` ne grimpent pas sans fin pendant une longue session.

### Physique

- [ ] Toutes les plateformes, checkpoints, kill bricks et décors sont ancrés.
- [ ] Les décors ont `CanCollide`, `CanTouch` et `CanQuery` à `false` quand c’est possible.
- [ ] Les objets du gameplay (kill bricks, checkpoints, pièces, SpawnLocation) ont gardé `CanTouch` à `true`.
- [ ] Aucun décor en MeshPart n’utilise `PreciseConvexDecomposition` sans raison (filtre `CollisionFidelity=PreciseConvexDecomposition` dans l’Explorer).

### Réseau

- [ ] Aucune animation décorative (pièces qui tournent, nuages qui flottent) n’est faite côté serveur.
- [ ] Aucun RemoteEvent n’est déclenché à chaque image, et chacun envoie le minimum de données.
- [ ] `ReplicatedStorage` ne contient que ce dont les clients ont besoin ; le reste est dans `ServerStorage`.

### Rendu

- [ ] Pas de zone où les FPS s’effondrent quand on la regarde.
- [ ] Peu de transparences partielles superposées (attention aux nuages !).
- [ ] Les lumières sans intérêt pour les ombres ont `Shadows` désactivé.
- [ ] Les maillages répétés partagent le même identifiant ; aucun n’est en `RenderFidelity` `Precise` sans raison.
- [ ] Les émetteurs de particules ont des taux raisonnables ; les textures ne dépassent pas la taille utile.

### Streaming

- [ ] `StreamingEnabled` est activé, avec les réglages recommandés vus à la leçon 3.
- [ ] Un test avec `StreamingTargetRadius` à 64 ne produit aucune erreur dans les LocalScripts.
- [ ] Aucun modèle n’est en `Persistent` sans vraie raison.

### Interface mobile

- [ ] Aucun bouton dans les coins inférieurs (voir la leçon 1) : le `BoutonBoutique` du module 5 est au bord gauche, à mi-hauteur ; vérifie aussi les boutons ajoutés depuis.
- [ ] Tous les boutons restent à portée de pouce, sur téléphone et sur tablette.
- [ ] Le texte est lisible sur un téléphone d’entrée de gamme (Device Simulator en **Physical size**, puis vrai appareil).
- [ ] Rien n’est caché par une encoche ou la barre de Roblox (`ScreenInsets` sur `CoreUISafeInsets`).

## Étape 3 : un script d’audit pour gagner du temps

Compter à la main les Parts non ancrées ou les lumières avec ombres est fastidieux. Ce script fait l’inventaire pour toi. Il ne modifie **rien** : il compte et affiche.

```luau
-- À exécuter dans la Command Bar de Studio (vue au module 1), en mode édition (pas pendant un test).
-- Copie tout le script, colle-le dans la Command Bar, puis appuie sur Entrée.
-- Ce script ne modifie rien : il compte et affiche le résultat dans l'Output.
local Workspace = game:GetService("Workspace")
local ReplicatedStorage = game:GetService("ReplicatedStorage")

-- Dossiers du fil rouge dont les Parts ont BESOIN du contact (Touched)
local dossiersGameplay = {}
for _, nom in { "Checkpoints", "KillBricks", "Pieces" } do
	local dossier = Workspace:FindFirstChild(nom)
	if dossier then
		table.insert(dossiersGameplay, dossier)
	end
end

local function estUnObjetDeGameplay(objet: Instance): boolean
	if objet:IsA("SpawnLocation") then
		return true -- le point d'apparition a aussi besoin du contact
	end
	for _, dossier in dossiersGameplay do
		if objet:IsDescendantOf(dossier) then
			return true
		end
	end
	return false
end

local compte = {
	parts = 0,
	nonAncrees = 0,
	decorsAvecContact = 0,
	transparencePartielle = 0,
	maillagesPrecis = 0,
	lumieresAvecOmbres = 0,
	emetteursParticules = 0,
	scripts = 0,
}

for _, objet in Workspace:GetDescendants() do
	if objet:IsA("BasePart") and not objet:IsA("Terrain") then
		compte.parts += 1
		if not objet.Anchored then
			compte.nonAncrees += 1
		end
		if objet.CanTouch and not estUnObjetDeGameplay(objet) then
			compte.decorsAvecContact += 1
		end
		if objet.Transparency > 0 and objet.Transparency < 1 then
			compte.transparencePartielle += 1
		end
		if objet:IsA("MeshPart") and objet.RenderFidelity == Enum.RenderFidelity.Precise then
			compte.maillagesPrecis += 1
		end
	elseif objet:IsA("Light") and objet.Shadows then
		compte.lumieresAvecOmbres += 1
	elseif objet:IsA("ParticleEmitter") then
		compte.emetteursParticules += 1
	elseif objet:IsA("LuaSourceContainer") then
		compte.scripts += 1
	end
end

print("===== Audit de l'Obby des Nuages =====")
print(string.format("Parts dans Workspace : %d", compte.parts))
print(string.format("Parts non ancrées : %d", compte.nonAncrees))
print(string.format("Décors avec CanTouch actif : %d", compte.decorsAvecContact))
print(string.format("Parts semi-transparentes : %d", compte.transparencePartielle))
print(string.format("MeshParts en RenderFidelity Precise : %d", compte.maillagesPrecis))
print(string.format("Lumières avec ombres : %d", compte.lumieresAvecOmbres))
print(string.format("Émetteurs de particules : %d", compte.emetteursParticules))
print(string.format("Scripts dans Workspace : %d", compte.scripts))
print(string.format("Objets dans ReplicatedStorage : %d", #ReplicatedStorage:GetDescendants()))
```

Ces chiffres ne sont pas des « notes » : il n’existe pas de nombre magique de Parts à ne pas dépasser. Ils te montrent **où regarder**. Par exemple, 40 Parts non ancrées dans un obby sans objets physiques, c’est suspect ; 25 scripts dans le Workspace, c’est peut-être un script de rotation copié dans chaque pièce.

<Astuce titre="Comparer avec ton appareil de référence">
La documentation propose une méthode : joue sur ton appareil de référence avec les statistiques de rendu affichées et repère à partir de quand les FPS chutent dans une zone chargée. Tu en déduis tes propres limites (par exemple un nombre d’appels de dessin à ne pas dépasser) pour la suite du développement.
</Astuce>

## Étape 4 : corriger, un problème à la fois

Classe ta liste : d’abord ce qui gêne le plus les joueurs selon tes mesures (pics, FPS bas sur mobile, plantages), ensuite le reste. Puis, pour chaque problème :

1. **Corrige-le** avec les techniques de la leçon 4 (et de la leçon 3 pour le streaming).
2. **Teste le gameplay** concerné.
3. **Mesure** dans tes conditions fixées.
4. **Note** le résultat dans ton journal (voir l’étape 6).

Pour l’Obby des Nuages, les corrections les plus probables sont :

- ancrer les Parts oubliées ;
- passer les décors (nuages, rambardes, îles décoratives) en `CanCollide`, `CanTouch` et `CanQuery` à `false`, et leur `CollisionFidelity` en `Box` ou `Hull` s’il s’agit de MeshParts ;
- remplacer la rotation des pièces côté serveur par le LocalScript de la leçon 4 ;
- vérifier que le compteur de pièces réagit à `Changed` (comme `ScriptInterface` au module 5) et ne tourne pas à chaque image ;
- réduire les nuages semi-transparents superposés et les lumières avec ombres ;
- vérifier les réglages de streaming et corriger les LocalScripts qui plantent avec un petit rayon.

<Erreur titre="Optimiser au point de casser le jeu">
Une optimisation qui casse une kill brick, empêche de valider un checkpoint ou fait perdre une sauvegarde est pire que le lag. Après chaque série de corrections, rejoue l’obby **en entier** : mourir sur une kill brick, valider chaque checkpoint, ramasser des pièces, acheter une traînée, quitter puis revenir pour vérifier la sauvegarde.
</Erreur>

## Étape 5 : vérifier le gain et traquer les régressions

Une **régression**, c’est quelque chose qui marchait et ne marche plus (ou des performances qui se dégradent après une mise à jour). Pour les repérer :

- **Rejoue tout le gameplay**, comme décrit ci-dessus.
- **Teste à plusieurs** dans Studio (mode serveur + 2 clients, comme au module 4) : les problèmes de LocalScripts et de streaming apparaissent souvent là.
- **Refais le test du petit rayon** (`StreamingTargetRadius` à 64) puis remets la valeur recommandée.
- **Remplis la colonne « Après »** de ta fiche, sur ton téléphone de référence. C’est là que le gain compte.

### Surveiller après la publication

Une fois la nouvelle version publiée, la page **Performance** du Creator Dashboard prend le relais. Dans le Creator Hub, ouvre **Creations**, choisis ton jeu, puis le menu **Monitoring** › **Performance**. Elle affiche notamment, ventilés par plateforme :

- la fréquence d’images des clients ;
- le taux de plantage des clients et les sorties inattendues par manque de mémoire ;
- la mémoire des clients et du serveur, et le heartbeat du serveur.

Tu peux aussi ventiler les métriques client par **version du place** (*Place Version*) pour comparer ta nouvelle version aux précédentes. Au moment de la rédaction (octobre 2026), la documentation indique que les graphiques nécessitent **au moins 100 utilisateurs actifs par jour** : sur un petit jeu, tes mesures manuelles restent donc essentielles.

<Info>
La documentation donne un repère : un peu de plantages est normal, mais un taux qui dépasse 2 à 3 %, ou une hausse soudaine juste après une mise à jour, mérite une enquête. Une hausse des sorties par manque de mémoire après une mise à jour signale souvent une fuite ou des ressources trop lourdes.
</Info>

## Étape 6 : documenter tes choix

Tiens un **journal de performance**. Un simple tableau suffit :

| Date | Changement | Avant | Après | Décision |
| :--- | :--- | :--- | :--- | :--- |
| 24/10 | Rotation des pièces passée côté client | … FPS zone 2 (téléphone) | … FPS zone 2 | Gardé |
| 24/10 | Nuages décoratifs : CanCollide, CanTouch, CanQuery à false | … | … | Gardé |
| 24/10 | `StreamingTargetRadius` réduit à 512 | … | décor lointain qui « pop » (apparaît d’un coup) | Annulé, retour à 1024 |

*(Remplace les « … » par tes propres mesures : chaque jeu et chaque appareil donne des résultats différents.)*

Ce journal t’évite de refaire deux fois la même expérience, explique tes réglages à un futur collaborateur, et te permet de retrouver vite la cause d’une régression.

<Defi titre="Ton audit complet">
1. Remplis la colonne « Avant » de la fiche de mesure, sur ton téléphone de référence.
2. Passe toute la checklist et lance le script d’audit dans la Command Bar.
3. Corrige au moins trois problèmes, un par un, en notant chaque mesure dans ton journal.
4. Rejoue tout l’obby, à un puis à deux joueurs.
5. Publie, puis remplis la colonne « Après ». Si ton jeu atteint le seuil d’affichage, garde un œil sur la page Performance pendant les jours suivants.
</Defi>

<Resume>
- Un audit suit le cycle : sauvegarder, mesurer (avant), passer la checklist, corriger un problème à la fois, mesurer (après), documenter.
- La checklist couvre scripts, mémoire, physique, réseau, rendu, streaming et interface mobile.
- Un script d’inventaire dans la Command Bar montre où regarder, mais ne remplace pas la mesure.
- Après chaque série de corrections, rejoue tout le gameplay pour éviter les régressions, puis vérifie le gain sur ton appareil de référence.
- Après publication, la page Performance du Creator Dashboard suit FPS, mémoire et plantages par appareil et par version.
</Resume>
